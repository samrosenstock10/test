## Substantive run

1. Read both complete bounded source tables, expanding the bounds if the final requested row is occupied. Map columns by their actual headers, fail on missing required columns or duplicate stable IDs. Read the complete current destination research tables and reconstruct the public feed as specified in `ai-infrastructure-research.md`, including `hydrateSheetReviews`. Reconcile against published main before making a candidate. Never start from a stale GitHub snapshot when the Sheet differs.
2. Load the optional Research Settings key `projectTrackerHandoff` (version 1, records object). Compute `sourceVersion(table, row)` for each source record. Scheduling-only changes to Claims Next Review do not make new evidence. Compare against state and destination provenance; there is no global date watermark that can discard an unreviewed item. Absence of state means an empty state, not permission to duplicate existing evidence.
3. Prioritize new/changed records with a concrete company or infrastructure bottleneck mechanism. Review at most three substantive candidates per normal run; zero is valid. Older unreviewed records remain eligible. Resolved Claims statuses are Validated, Partially validated, Contradicted and Abandoned. Open, Too early and Unverified remain upstream; a numeric target or resolution label alone is not verified delivery. Contradicted/abandoned outcomes are useful counterevidence, not successes.
4. Read the original public primary source for selected records, and the resolution source for Claims. State the actual access scope and incentives. Keep original deployment facts and original claim/target separate from our investment interpretation. No public winner, utilization, margin or return claim follows automatically from capacity added. Notes-only/catalog-only records must remain leads. If access is insufficient, defer or save an explicitly limited lead; never pretend a resolution was verified.
5. Compare the same underlying source plus substantive claim against destination Evidence Register AND Expert Research. Preserve original issuer/customer origin as the independence group, never the tracker or assistant. Same evidence in the two trackers is intentional. A repeated source is not independent corroboration. Use `link` for an already represented claim (including a paraphrase); this stores the source-ID mapping in handoff state without rewriting immutable evidence. A distinct claim from the same source requires `distinctClaimReason` and shares the existing origin. Conflicting origin labels require attribution review. Follow D4's relevant Muse provenance checks; an unavailable peer read is a logged gap, not invented completion.
6. Call `planProjectHandoff` with `{source: {Bottlenecks: [...], Claims: [...]}, feed, state, observedAt, decisions}`. Each decision has `table`, `sourceId`, the exact reviewed `version`, `action` (import/link/skip) and `reason`. `link` adds `existingEvidenceId`; `skip` records a reviewed relevance decision for that version. Omitted/deferred items remain pending. For `import`, supply `evidence`: title, summary, claim, interpretation, independenceGroup, publishedDate (null if unknown), contentAccess, status, verification, countercase and nextTest. Date fields preserve the source's real dates, not the handoff date. Input rows contain original Sheet headers; do not silently rename them.
7. The helper returns additions, outcomes, pending, state and a full feed. IDs depend on upstream table ID and material source version, so replay after a partial write does not duplicate. Changed records append a new ID and `supersedes`; published originals stay immutable. It preserves all non-evidence research fields. Require the full existing `prepareResearchCandidate` validation as well. Check that every cell stays under 45,000 characters; if state eventually needs partitioning, log that bounded maintenance issue and retain pending work rather than truncating it.
8. Immediately re-read selected source rows and destination append bounds/settings state before mutation; if anything relevant changed, rebuild. Save additions to Evidence Register (ID, Title, Source group, Published, Access, Summary, Record JSON) and returned state under Settings key `projectTrackerHandoff` in one Sheets batch. Preserve native formatting and other records. Read back exact cells and compare parsed JSON, IDs and version mappings. Do not advance state on an unverified/failed write. A retry must read the live destination first.
9. In the existing expert Research Runs review JSON, record `projectTrackerHandoff` with status, selected source IDs/versions, added/linked/skipped IDs, pending count, access/attribution gaps and publication state. This does not mark untouched podcast lanes or a weekly conviction review complete. Configuration/bootstrap work uses a separately labeled run and never consumes a scheduled source cycle. If source access fails, log the gap, keep last verified data and continue the otherwise authorized expert task.
10. Publish only a semantic change through the existing protected one-candidate runtime PR. Reconstruct the entire candidate from the verified canonical Sheet; do not publish the helper's earlier in-memory snapshot after other Sheet changes. Never write the production feed directly or merge the runtime PR yourself. Verify generated main and the site's existing feed read path. A linked/skip-only result needs no public publication. Publication recovery uses verified Sheet state, not a second import.
